# SecureFlow Safe Upgrade Guide

This guide provides operators and self-hosters with a standardized, step-by-step checklist for upgrading SecureFlow safely between releases, applying database migrations, validating system health, and executing a zero-data-loss rollback if necessary.

---

## 📋 Pre-Upgrade Checklist

Before initiating any upgrade, complete each item in this checklist:

- [ ] **1. Read the Release Changelog**: Review [`CHANGELOG.md`](../CHANGELOG.md) (generated by Changesets) for breaking changes, new features, and deprecated configurations.
- [ ] **2. Back Up Database**: Take a full PostgreSQL snapshot before any schema changes run.
- [ ] **3. Review Environment Variables**: Compare your `.env` with [`.env.example`](../.env.example) for newly required or changed variables.
- [ ] **4. Pull New Image / Artifacts**: Fetch the target container image tag or pull the release branch.
- [ ] **5. Run Schema Migrations**: Apply Prisma database migrations (`prisma migrate deploy`).
- [ ] **6. Verify System Health & Version**: Probe `/api/health` and `/api/version` to verify successful deployment.
- [ ] **7. Prepare Rollback Plan**: Know the exact commands to restore the previous image and database dump if issues arise.

---

## 1. Step 1: Read the Changelog

Every release records changes, security advisories, and database migration notes in the centralized changelog:

- **Application & Server Changelog**: [`CHANGELOG.md`](../CHANGELOG.md)
- **CLI Tool Changelog**: [`cli/CHANGELOG.md`](../cli/CHANGELOG.md)

Pay close attention to sections marked **Breaking Changes** or **Migration Notes**, which specify whether manual interventions (such as index reindexing or credential rotations) are required.

## 2. Step 2: Back Up the PostgreSQL Database

Always create a full database dump prior to upgrading. This ensures you can return to a known working state if a migration fails or a schema change introduces unexpected behavior.

### Option A: Docker Compose Deployments

```bash
# Set timestamp variable
BACKUP_FILE="secureflow_backup_$(date +%Y%m%d_%H%M%S).sql"

# Export PostgreSQL dump from container
docker compose exec -T postgres pg_dump -U postgres secureflow > "$BACKUP_FILE"

# Verify backup size is non-zero
ls -lh "$BACKUP_FILE"
```

### Option B: External / Managed PostgreSQL (RDS, Neon, Supabase)

```bash
# Using pg_dump custom archive format (compressed, supports parallel restore)
pg_dump -Fc -v --no-owner --no-privileges "$DATABASE_URL" -f "secureflow_backup_$(date +%Y%m%d_%H%M%S).dump"
```

> ⚠️ **Important**: Store backups on external, durable storage separate from the container host.

## 3. Step 3: Pull New Container Image or Code

### Docker Compose

Update the image tag in your `docker-compose.yml` (or pull the latest image):

```bash
# Pull updated images for app and worker
docker compose pull app worker migrator
```

### Kubernetes (Helm)

Update your Helm release values with the new target version:

```bash
helm upgrade secureflow ./helm/secureflow \
  --reuse-values \
  --set image.tag="v0.2.0"
```

### Bare-Metal / Git Deployments

```bash
git fetch origin --tags
git checkout tags/v0.2.0
npm ci --legacy-peer-deps
npm run build
```

---

## 4. Step 4: Check New Environment Variables

New releases may introduce optional or required configuration flags. Compare your active `.env` against the reference `.env.example`:

```bash
# Check diff between template and active env
diff -u .env.example .env | grep "^+ "
```

Key recent configuration additions to check:
- `OTEL_EXPORTER_OTLP_ENDPOINT`: OpenTelemetry distributed trace collector URL (optional).
- `DATA_RETENTION_DAYS`: Auto-purge threshold for findings and scans (optional).
- `TRUSTED_PROXY_HOP_COUNT`: Reverse proxy hop count for rate limit accuracy (recommended behind ingress/Cloudflare).
- `AI_PROVIDER` & `AI_MODEL`: Custom LLM gateway overrides.

## 5. Step 5: Run Database Migrations

SecureFlow uses Prisma for schema management. Migrations must be executed using `prisma migrate deploy`, which applies pending SQL migrations idempotently without resetting or modifying existing data.

### Option A: Dedicated Migrator Container (Recommended for Docker)

The Docker deployment includes an isolated `migrator` stage that runs as non-root user:

```bash
docker compose run --rm migrator
```

### Option B: Manual CLI Execution

```bash
npx prisma migrate deploy
```

Verify that all migrations applied cleanly with exit code `0`.

---

## 6. Step 6: Start Services & Verify Health

Launch the updated services:

```bash
docker compose up -d
```

### 1. Verify Application Health Probe (`/api/health`)

Query the health check endpoint to confirm database, Redis, and AI subsystem availability:

```bash
curl -f -s http://localhost:9002/api/health | jq .
```

Expected output:
```json
{
  "status": "healthy",
  "components": {
    "database": { "status": "healthy", "latencyMs": 5 },
    "redis": { "status": "healthy", "latencyMs": 2 }
  }
}
```

### 2. Verify Running Version (`/api/version`)

Query the version endpoint to confirm that the container is executing the intended build:

```bash
curl -s http://localhost:9002/api/version | jq .
```

Expected output:
```json
{
  "version": "3.8.0",
  "commit": "fe24fd56",
  "buildDate": "2026-11-20T23:25:00Z"
}
```

You can also verify the version in the bottom bar of the **Mission Control Dashboard** (`/dashboard`).

## 7. Step 7: Rollback Procedure (Plan B)

If an upgrade fails, health checks report errors, or critical functional regressions occur, follow these rollback steps immediately:

### 1. Stop the New Services

```bash
docker compose down
```

### 2. Revert to the Previous Container Tag

Update your `docker-compose.yml` or `helm` values back to the previously running version tag (e.g. `image.tag: "v3.8.0"`).

### 3. Restore the Database (If Migrations Were Incompatible)

If the new version executed breaking schema migrations, restore the database from your Step 2 backup:

#### For SQL Plain-Text Dump:
```bash
docker compose exec -T postgres psql -U postgres secureflow < "$BACKUP_FILE"
```

#### For Custom Archive (`.dump`):
```bash
pg_restore --clean --if-exists -d "$DATABASE_URL" "secureflow_backup_XXXXXX.dump"
```

### 4. Restart Previous Version

```bash
docker compose up -d
```

### 5. Validate Restored Service

Verify that the rollback succeeded and the system is fully operational:

```bash
curl -f http://localhost:9002/api/health
curl -s http://localhost:9002/api/version
```
